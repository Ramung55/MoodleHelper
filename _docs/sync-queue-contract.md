# Issue 19: resumable mock scan queue contract

## Goal

Provide a durable selected-course mock scan queue driven by the extension service worker and backed by the existing local FastAPI SQLite authority. The mock produces deterministic synthetic results only; it does not access Moodle. A restarted worker can resume unfinished jobs without repeating committed results.

## Acceptance criteria

- [ ] Starting a mock run with selected existing course IDs exposes persisted pending, running, completed, failed and cancelled job states and progress through the documented API; readback after backend or worker restart reflects committed state. Progress reports terminal and total counts and per-job state, not a fabricated percentage of Moodle work.
- [ ] Kill and recreate the production extension queue worker against real HTTP and a temporary file SQLite database during an unfinished job. Recovery reclaims it after its lease expires, finishes it, retains already completed jobs without executing them again, and leaves one durable result per job. Include crashes before and after the atomic commit.
- [ ] Concurrent starts with overlapping course IDs in one namespace atomically share the existing active job for each overlap, including concurrent requests and worker restart; no two pending/running jobs for a course exist. Repeating a start with the same idempotency key returns the same run; a reused key with different course IDs is rejected. Distinct subsequent runs can rescan after terminal jobs.
- [ ] Cancellation atomically cancels pending jobs and fences running claims for the cancelled run. Completed results remain available; a late in-flight reply cannot commit a result or make the cancelled run successful. Repeated cancellation is safe; a run already completed remains completed. Shared jobs remain runnable for any other non-cancelled run that references them.
- [ ] Default active concurrency is one, configurable and bounded as documented below. With concurrency greater than one, a failed job records a safe error and unrelated jobs finish. Tests check the maximum active executor calls, terminal aggregate counts and independent failure.
- [ ] Versioned source OpenAPI describes the new HTTP operations and exact schemas, errors, binding and limits before backend implementation; generated OpenAPI parity and existing API behavior remain intact. Tests cover namespace isolation, transactional rollback, stale claims, cancellation races, idempotency, invalid input and bounded requests.

## Out of scope

- Real Moodle collection, request pacing and live-site compatibility: [#20](https://github.com/Ramung55/MoodleHelper/issues/20). Progress/cancellation screens: [#21](https://github.com/Ramung55/MoodleHelper/issues/21). This issue supplies the durable API and a mock worker, not UI or a live Chrome/SDU claim.

## Constraints and decisions

### Authority and identity

SQLite is authoritative for runs, jobs, links, claims and mock results, scoped by the trusted namespace selected at backend startup (#5/#6). No request selects a namespace. Add a transactional versioned migration; preserve existing Snapshot JSON, revision and API. Queue records are separate from Snapshot and its existing course sync state. Synthetic mock results are queue-owned records, not source observations and do not alter Snapshot. Do not create another persistence engine or silently use extension storage as authority. Existing loopback-only trust policy applies; no account, credentials, request-selected identity or broad permissions. HTTP endpoints use the existing process bridge binding for mutations, and stale binding returns 409; a worker reconnects after backend restart. Reads are subject to the same local trust boundary. Enforce closed request schemas, fixed routes, bounded payloads and safe error envelopes, never expose SQL, tracebacks, tokens or raw executor exceptions.

### Model and API contract

Document exact source OpenAPI schemas before implementing: a run has immutable ID, idempotency key and normalized unique selected course IDs, creation time, status, cancellation flag and references to jobs; a job has immutable ID and course ID, state, attempts, lease/claim generation and safe error code, and a unique optional synthetic result. Statuses are pending/running/completed/failed/cancelled. Run state is cancelled if explicitly cancelled, otherwise running while any linked job is running, pending while unfinished jobs remain, failed if all terminal and any failed, otherwise completed. Progress is counts by job state plus total; cancellation is represented per run even where a job is shared. Store run-to-job links so overlapping runs share work. Run status and counts must be derived consistently in a single read transaction; do not count a shared job twice within a run.

Specify fixed operations to create a run, read a run with paged jobs, cancel a run, claim work, renew a claim, and finish a claim. Require a bounded opaque idempotency key and 1–100 unique IDs of existing selected courses; reject unknown, duplicate, malformed or oversized input without side effects. Normalize IDs by sorted order for key comparison. Server assigns random opaque IDs. Cap pages at 100 and expose stable pagination; do not load all historical queue records in memory. Public claim/finish fields contain only narrowly typed mock data and a claim token, never URLs or arbitrary operations. Error responses use existing {message} convention: validation 422, absent run 404, conflicting idempotency/stale claim/context 409, storage unavailable 503. Document exact route names, field lengths, safe codes and generated contract parity. Existing backend namespace and localhost are a trust boundary, not authentication.

### Transaction and worker lifecycle

Each enqueue, claim, renew, cancel and finish is an atomic SQLite transaction using the same transaction discipline as Snapshot writes. Use database constraints/transactional serialization to enforce one active job per namespace/course, unique run/key, unique run/job and one result per job. Enqueue atomically attaches overlapping active jobs and creates missing jobs; terminal jobs are never reused for a new scan. A start replay returns its original run even after termination. A job is eligible only while at least one non-cancelled linked run needs it. Claim pending jobs in deterministic creation/ID order with an expiry, a monotonically increasing generation and unguessable token. Finish or renew succeeds only for the current unexpired generation/token, with an eligible linked run. Each result and completed transition commits together; executor output is deterministic from job/course ID, with a stable result identity. A crash before commit is retried; a crash after commit sees completed state and never executes it again. A stale worker's finish is rejected even if it returns after cancellation or reclamation. Do not promise exactly-once execution: retries may execute unfinished mock work more than once, but commits are idempotent. Failures become terminal failed with a bounded allowlisted code, not raw exception text; they do not stop scheduling others. No implicit retry of failed jobs; a new run is the explicit retry.

Cancel transaction marks the run cancelled and removes its demand. Pending or running jobs with no other live demand transition to cancelled and invalidate their claim generation; shared jobs retain their state and can finish for remaining live runs. Completed and failed jobs and results are retained. Cancel/finish races resolve by SQLite transaction order: finish committed first retains its result; cancellation first fences a sole-demand claim. A cancelled run always remains cancelled. On backend restart bindings rotate; persisted claims expire normally and new workers obtain fresh binding. Lease expiry makes a running job reclaimable; old generations cannot commit. A bounded renewal interval and lease length must be documented and tested with an injected clock. At most one active valid claim per job and a namespace-wide concurrency cap enforced atomically in SQLite, including multiple worker instances. Set default 1, configure a startup integer 1–4; invalid values fail startup with a safe message. Lowering the cap lets existing unexpired claims finish and grants no new claims until below the cap.

The actual MV3 worker installs a production queue service and resumes it on worker startup and on a bounded Chrome alarm while unfinished jobs exist. Declare only the narrowly necessary alarms permission; no new dependency. A wake reconnects, reclaims expired jobs and drains within the configured limit. Alarm and event listeners are registered synchronously; worker memory is disposable. Stop/recreate the actual queue service in tests rather than calling a job function twice; injectable clock/executor/transport are allowed. If backend is unavailable, do not mark jobs successful or failed: retain state and retry on a later wake. No unbounded timers, maps or active promises; cap dispatch and page size. Document lease, alarm, startup configuration and local run commands in README/architecture. No live Chrome interruption or Moodle integration is claimed solely from mocks.

### Verification and handoff

Use existing uv, TypeScript/Vitest and approved SQLAlchemy, with no added dependencies. Cover genuine worker destruction/recreation using production queue abstraction, controlled executor gates and actual HTTP/SQLite; race overlapping starts and cancellation against finish; test rollback and migration from current database; assert existing Snapshot changes and overlays survive, namespace isolation and old contract parity. Exercise backend restart with binding rotation and lease expiry, persistence and no completed reruns. Run relevant backend, browser-workspace tests and existing contract checks; report exact results to independent QA. Do not close the issue as engineer.

### Production wakeup clarification

Keep one named Chrome alarm with a one-minute period even when the queue is idle, rather than removing it when idle. Chrome may terminate the worker between alarm events; the alarm wakes the installed worker, which reconnects and checks for eligible jobs. Register listeners synchronously and ensure the alarm exists on installation and worker startup; create/recreate it idempotently. A direct local HTTP run creation persists the run and returns without claiming immediate execution; the next alarm discovers it, normally within one alarm period subject to Chrome scheduling and backend availability. No dashboard UI or extension runtime start message is required. If the backend is unavailable, retain the alarm and retry on the next wake without changing job state. The fixed loopback routes, binding, origin and local trust constraints above remain unchanged; alarms is the only required extension permission for this wakeup.

Test the installed production worker entry point with simulated Chrome alarm/event APIs, actual HTTP and SQLite: let it become idle, create a run directly through HTTP, dispatch the registered alarm, and assert the mock executor runs and persists completion. Destroy and recreate the worker, confirm listener/alarm registration and recovery. Calling an unattached queue-service method alone does not demonstrate the production initiation path. This clarification replaces the earlier instruction to keep an alarm only while unfinished jobs exist.
