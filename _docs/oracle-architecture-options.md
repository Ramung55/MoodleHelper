# Варианты публикации и Oracle: план архитектуры (2026-11-13)

**Это анализ, а не развёртывание.** Облачные ресурсы не создавались и не менялись, приложение не публиковалось. Выбор архитектуры остаётся за владельцем. Основано на коде ветки `feat/issue-95-page-refresh` (от `main` `6192dab`), [oracle-deployment.md](oracle-deployment.md), [local-process-auth.md](decisions/local-process-auth.md), `docker-compose.production.yaml`, `Caddyfile.oci`.

## Что есть сейчас (проверено по коду)

- Dashboard на GitHub Pages (`https://ramung55.github.io/MoodleHelper/`) уже ходит в локальный backend `http://127.0.0.1:8000` (`frontend/src/services/api-base.ts`). Backend разрешает по CORS только этот origin, без credentials, с Private Network Access (`backend/main.py`, `CORSMiddleware`).
- `LoopbackHostMiddleware` отвечает 400 на любой `Host`, кроме `127.0.0.1`, `localhost` и `[::1]`. Поэтому в `Caddyfile.oci` стоит `header_up Host localhost`.
- Привязка процесса (`X-Moodle-Helper-Bridge-Binding`) — защита от устаревших и межсайтовых записей, **не авторизация**: её получает любой вызывающий через `GET /api/bridge-context`.
- Расширение жёстко нацелено на `http://127.0.0.1:8000` (`extension/src/dashboard-bridge.ts`, `BACKEND`), `host_permissions` — только этот адрес и `moodle.sdu.edu.kz`. Moodle читается в браузере студента его собственной сессией. Облачный сервер не может и не должен читать Moodle сам.
- Идентичность датасета — `MOODLE_HELPER_STABLE_USER_ID` в пространстве имён (#93). Live-данные сохраняются только при совпадении аккаунта Moodle.

## Проблема 401 с Caddy

Что зафиксировано в [oracle-deployment.md](oracle-deployment.md): в изолированном Compose-стенде страница открывается после Basic Auth, а API-запросы dashboard получают 401.

Почему: Basic Auth в Caddy защищает **все** маршруты. Браузер повторно отправляет сохранённые Basic-credentials только на запросы с `credentials: 'same-origin'` или `'include'`. Frontend намеренно вызывает API с `credentials: 'omit'` (`http-adapter.ts`, `ai-gateway.ts`, `ai-fallback.ts`), потому что в варианте A никаких cookies и credentials быть не должно. Поэтому каждый `fetch` к `/api/...` уходит без заголовка `Authorization` и получает 401. Контрольный запрос с `same-origin` дал 200.

Возможные решения (ни одно не применено):

1. **Режим «hosted» во frontend с `credentials: 'same-origin'`** только когда dashboard открыт с того же origin, что и API. Минимальная правка кода, но Basic Auth остаётся единственной защитой: нет выхода, нет rate limiting, одна общая учётная запись. Тогда же нужен CSRF-анализ: межсайтовая форма не отправит кастомный заголовок привязки, так что текущий `bridge_precondition` частично покрывает CSRF, но это нужно проверить отдельно.
2. **Сессионная авторизация в самом backend** (вход, HttpOnly `SameSite=Strict` cookie, CSRF-токен) вместо Basic Auth. Правильное решение для B, но это новая функциональность и security review.
3. **Приватный доступ без публичного входа**: VPN или туннель (например, WireGuard или Tailscale), Caddy слушает только приватный интерфейс. Не нужно менять клиентский контракт, но доступ только с устройств владельца.
4. **Нельзя:** снимать `basic_auth`, ослаблять `LoopbackHostMiddleware` или выставлять порт приложения наружу ради исчезновения 401.

## Рекомендация

**Сейчас — вариант A, без Oracle.** Он уже реализован (Pages + локальный backend) и не меняет модель приватности. Для MVP нужно закончить live-проверку (#95, #96), а не облако.

Oracle имеет смысл позже и только для варианта B, если владелец решит, что данные можно хранить вне устройства. Вариант C — отдельный продукт.

Порядок задач до любой публикации:

1. Слить #95 после независимого QA и пройти #96 на настоящем SDU Moodle (владелец входит в Moodle сам).
2. Для варианта A: инструкция установки (backend + расширение), проверка Pages → `127.0.0.1` в актуальном Chrome (Private Network Access), упаковка расширения.
3. Решение владельца по B: можно ли хранить данные на сервере, какой метод доступа (решение 2 или 3 выше).
4. Если B: issue на auth-слой и hosted-режим frontend; issue на адрес и разрешения расширения; issue на backup/restore PostgreSQL; security review; затем изолированный staging.
5. Только после этого — проверка Oracle и staging (ниже), затем отдельное решение о публичном доступе.

## План проверки Oracle Always Free (выполнять владельцу или с его разрешения)

1. Console → Governance & Administration → Tenancy Management → Limits, Quotas and Usage: остаток A1 (документация Oracle на 2026-11-13: 1500 OCPU-часов и 9000 GB-часов в месяц для `VM.Standard.A1.Flex`, для Always Free tenancy это 2 OCPU и 12 GB; **сверить в Console**), boot + block volume (200 GB суммарно в домашнем регионе, 5 backup; минимальный boot volume документация называет то 47, то 50 GB), публичные IP.
2. Домашний регион, текущие VM, VCN, security lists и NSG — только просмотр.
3. Включить бюджет и оповещения о расходах до создания чего-либо (бюджет предупреждает, но не останавливает списание).
4. Проверить, что образ помечен **Always Free Eligible** (Ubuntu ARM64), и есть ли capacity A1 (возможна ошибка «Out of capacity»).
5. Учесть отзыв простаивающих VM: Oracle считает VM простаивающей, если за 7 дней 95-й перцентиль CPU, сеть и (для A1) память ниже 20%. Однопользовательский MoodleHelper почти всегда под этим порогом.

Цифры выше взяты из документации, а не из аккаунта: в этой сессии Console Oracle не открывалась. Источник: [Oracle Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).

## Совместимость ARM64

Подтверждено ранее (2026-11-12, [oracle-deployment.md](oracle-deployment.md)): у базовых образов есть `linux/arm64`, Python- и frontend-зависимости ставятся под эмуляцией, backend импортируется. **Не подтверждено:** полный `docker buildx build --platform linux/arm64` (Vite завис под эмуляцией), весь Compose-стек и браузерный путь на ARM.

План:

1. Закрепить digest образов и версию Bun в `Dockerfile` (сейчас Bun не закреплён).
2. Нативная ARM-сборка (на самой A1 VM или в ARM CI-раннере), а не эмуляция.
3. На изолированном staging: `pytest`, Compose health, браузерный сценарий dashboard, persistence после перезапуска, backup/restore PostgreSQL, проверка авторизации на каждом маршруте и TLS-сертификата.
4. Только после этого — решение о публичном DNS.

## Что неизвестно

Текущие ресурсы, расходы и регион аккаунта Oracle; фактическая доступность A1; решение владельца о хранении данных вне устройства; работает ли Private Network Access из Pages в той версии Chrome, которой пользуется студент (не проверялось в этой сессии).
