# Source deadline tracking design (#22)

## Identity and assertions

Track each stream under its existing namespace-scoped reconciliation source association ID. That ID includes the course, source kind, durable raw record identity and occurrence where applicable. Keep the original assessment ID and association on history; resolve the assessment through reconciliation aliases when displaying it. Confirmation or rejection of a pair does not compare streams or create events. Unassociated or ambiguous records have no trackable stream.

Only assignment due and quiz closing observations support deadline assertions. Their existing known `DateValue` is a known assertion. Add the optional field `syntheticDeadlineRemoval: true` on these raw DTOs as an explicit, synthetic-only removal assertion. Reject it outside the injected synthetic collection context, and reject a payload combining it with any due/closing value, including unknown. Absence, unknown and parse failure are not assertions. No live Moodle null or absence implies removal. Calendar start/end have no established deadline meaning.

Add optional Snapshot stream state containing association ID, original assessment ID, observation watermark, optional last accepted assertion with its observed time and URL, and whether a known value has ever established the stream. An unknown-only stream persists its watermark even before an accepted assertion exists. An assertion is a DateValue or an explicit `{kind: "removed"}` branch, never null or unknown. Extend only DeadlineChange's `from` and `to` union with this removed branch, preserving all legacy records. New events additionally carry source association ID, source URL and source observed time; legacy events have no invented attribution. Capture `detectedAt` separately at acceptance. Optional state and event fields are non-null on wire.

## Ordering and bootstrap

Only valid zoned observation instants participate. Compare exact deadline instants by instant, retaining original offset and timezone; compare date and week values at their own precision. Different precision is not equal. The first known value establishes a baseline without an event. An initial removal is remembered as a provisional removal without history; the first known value still establishes the baseline without an event. Once established, known-to-removed, removed-to-known, and subsequent changes each create an event, including A→B→A.

Each stream also has an observation-order watermark, separate from the accepted assertion time. Every valid, associated observation advances it, including unknown or missing dates and equivalent assertions; malformed timestamps are rejected. A failed/unavailable collector with no associated observation cannot advance any stream. Assertions older than this watermark remain raw evidence only. At the watermark instant a known assertion can follow an unknown observation, but contradicting an already accepted assertion at that instant rejects the entire refresh transaction, including all records and receipts. Equivalent assertions are replays. A later unambiguous observation can proceed. A batch containing same-time contradictions is also rejected atomically. Unknown/missing observations never replace the accepted assertion.

Legacy Snapshots have no stream state. On the first newly ingested assertion for such a stream, seed it from that assertion without inventing historical events; historical raw records and old history remain intact. If the first refresh contains several assertions for a stream, validate and order them, reject contradictory equal-time assertions, and seed only the newest unambiguous assertion without creating events. A replay used for seeding does not become a change. Explicit Snapshot replacement replaces tracking state along with the rest of the Snapshot; restore does not synthesize transitions.

## Projection and transactions

Accepted stream state is the authority for both backend matching/projection and frontend source-date selection and override conflict, never a raw latest record. Raw collection observations and original assessment evidence remain available as provenance. For associated Moodle sources with tracking state, consumers select from accepted known assertions only; a removed stream contributes no deadline. For multiple independent Moodle associations on one logical assessment, select the known assertion with the greatest accepted observed instant; break equal-time ties deterministically by association ID. This selection does not compare streams for changes. Untracked legacy evidence may contribute only when it can be associated uniquely with an untracked stream; suppress ambiguous evidence rather than attributing it by source kind. Wholly unassociated legacy assessments, including sample snapshots, retain their existing source display. In particular a removed tracked stream's old raw evidence must never be revived by legacy fallback. If no eligible Moodle stream contributes a known value, use a known syllabus value under the existing #33 fallback, otherwise show unknown. Both backend and frontend must share these rules; retained unknown, stale or contradictory evidence must never become the effective source date or conflict.

For an override, compare its unchanged baseline against the selected source date; removal is a visible conflict when it removes the selected source date, including when no fallback exists. If a syllabus fallback becomes selected, show its source and value while preserving the original personal date and baseline. The assessment sheet renders the original and new precision, source kind and URL, observed and detection times for each event; legacy history is explicitly unattributed. Source changes never alter overlays. Syllabus mock import identifies candidates by stable document digest and row; a changed document has a different source association and is not a same-stream update. This issue detects supported assignment and quiz ingestion without claiming that this mock import detects syllabus document revisions.

Validate, append raw evidence, update stream state, append history, reconcile and project inside the same current-state `store.mutate` transaction. SQLite's `BEGIN IMMEDIATE` serializes writers; failures after writes roll back the whole mutation, including overlays. The Snapshot carries state through backup/restart. Source OpenAPI precedes coordinated Python, Zod, bridge and contract parity changes. No live source support is claimed by the synthetic fixture assertion.
