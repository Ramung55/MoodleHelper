# Issue 21: sync progress and freshness — PM handoff

## Goal

Show durable, explicitly mock scan progress and honest freshness on the dashboard and extension popup, while keeping saved student data visible. This issue does not make the blocked live scan operational.

## Acceptance criteria

The five original criteria in [#21](https://github.com/Ramung55/MoodleHelper/issues/21) remain unchanged and all must pass:

- [ ] Dashboard and popup provide start/cancel controls and display per-course progress using mock run states.
- [ ] Successful full sync time is distinct from an individual-page refresh and from the last attempted failed run.
- [ ] Partial, failed, cancelled, and signed-out examples display distinct labels and actionable retry/login controls.
- [ ] The previous data stays visible with freshness information during a new or failed scan.
- [ ] Starting again during an active scan cannot create duplicate runs; no successful sync yet is stated explicitly.

## Out of scope

- Durable queue execution is [#19](https://github.com/Ramung55/MoodleHelper/issues/19); real source, collection and pacing remain [#20](https://github.com/Ramung55/MoodleHelper/issues/20), which is blocked per [QA](https://github.com/Ramung55/MoodleHelper/issues/20#issuecomment-6439166819) and [orchestrator](https://github.com/Ramung55/MoodleHelper/issues/20#issuecomment-6439178046). Browser notifications are [#39](https://github.com/Ramung55/MoodleHelper/issues/39). No original criterion is moved out.

## Constraints and implementation contract

- Follow root and frontend AGENTS.md, process, and the existing architecture; no new dependencies without permission. Preserve existing working dashboard, the #9 bridge security, #18 page receipts and #19 queue safety. No installed Chrome or live Moodle claim from simulated evidence. No UI automation is required or authorized for this handoff.
- Actual changes are necessary in `frontend/src/routes/index.tsx` and its store/adapters and `extension/public/popup.html` plus popup script/build wiring; the popup is currently empty. Keep the established frontend design and functional features. The active goal authorizes finishing the expanded backlog and preserving the frontend; this issue explicitly calls for both UI surfaces. An earlier optional UI label edit was rejected by automatic review: the engineer must respect any applicable reviewer restriction and must not bypass it. If an actual necessary edit is rejected, report the exact blocked action and reason rather than claiming completion; an unrelated past rejection alone does not establish that every issue-21 edit is prohibited.
- Expose mock queue start/read/cancel through fixed, closed, source-OpenAPI-first operations and corresponding generated schemas, shared inventory, worker and dashboard bridge. Reuse trusted startup namespace and process binding; never accept caller-selected namespace, target, headers or identity. The existing queue has per-ID read only, no list/current-run discovery, and does not prevent two differently keyed runs sharing jobs. Add a bounded, namespace-scoped discovery/readback and an atomic start-or-return-active operation for the same selected course set across dashboard and popup, including concurrent starts. Retain #19's overlap sharing and cancellation fencing. Document ordering, bounds, stable pagination and terminal selection. Tests must cover restart and simultaneous clients. Do not change `/api/sync` live fail-closed behavior.
- Both surfaces use the same authoritative backend records and tracked course IDs from Snapshot; empty selection gives a clear action to select courses. Name course jobs from saved course IDs, show pending/running/completed/failed/cancelled and aggregate progress. Label this explicitly as a mock run; completion is not Moodle sync or a data refresh. Refresh by bounded polling while visible, stop on disposal, and reload durable state on reopen; delayed responses must not overwrite newer state. A cancellation request must not optimistically report success: resolve backend response/reread, preserve cancelled terminal state even if a late completion arrives, and handle shared jobs honestly. A timeout or process-binding change means outcome unknown: offer reconnect and readback before an explicit retry; never automatically replay a mutation with a new key. Keep a stable key for the same unresolved start and reconcile across surfaces.
- Snapshot `sync[].lastSuccessAt` is per-course and sample/demo values are demo; its maximum is not evidence that an entire selected set completed a real full scan. Display a full-sync timestamp only when an authoritative record explicitly attests complete full-scan coverage of the relevant set, otherwise “No successful full sync yet”; mark any existing demo timestamps as demo. Mock completion never sets that timestamp. Separately show the latest applicable #18 page receipt with its observed time, scope, outcome and synthetic/verified evidence label, and the last failed attempt with an actual recorded attempt time; do not invent a failure or completion time. Existing queue provides only createdAt, so label that as attempt started, not failure completion. If authoritative full-scan evidence does not exist, state that rather than infer it.
- Provide distinct mock example states for partial, failure, cancellation and signed-out using deterministic injected fixtures/model tests and visible renderable examples, unmistakably marked examples. Partial means mixed/incomplete coverage; failed means a recorded mock failure; cancelled means the run was cancelled. Signed-out example must offer the fixed SDU Moodle login URL and retry guidance but must not claim the current browser is signed out, collect credentials or enable a real scan. Retry explicitly creates a new mock attempt after a terminal outcome, with selected courses and fresh key; no retry is allowed to duplicate an active run. For backend unavailable or storage/bridge failures show safe actionable reconnect/retry guidance, retain the last confirmed Snapshot and timestamps and do not present stale progress as current.
- QA must independently exercise both rendered surfaces and their real event handlers with labeled mock states, including all original criteria, partial/failure/signed-out examples, absent and existing full-sync evidence, page receipt scope, no selection, repeated/concurrent starts, cancelled/late finish, network loss, uncertain write, backend restart, reopening, stale polling responses and prior data retention. Use actual loopback HTTP and isolated SQLite for queue/readback races, and explicitly labeled Chrome/window shims for popup/bridge where required. Verify source/generated schemas, closed message boundaries and no regression to existing sync/collection behavior; run appropriate suites/builds. Distinguish simulated UI/browser from actual Chrome or SDU observations. Engineer records results and commit; independent QA rereads original criteria and reports PASS/FAIL before closure.
